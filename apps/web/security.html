Security

What protects your files, what it does not protect against, and how to help find and fix problems.

What protects your files

  • Encryption happens in your browser. Files and names are encrypted with AES-256-GCM through the browser's built-in Web Crypto. Keys come from HKDF-SHA-256 over a 32-byte random secret. Nonces are derived from the content (synthetic), so they never repeat, and a parcel opens under exactly one key (key commitment).
  • The key stays in the link. The secret lives after the # in the link, which browsers never send to servers. Servers store only a hash of a token derived from it, which admits a browser to the room and cannot decrypt anything.
  • Every piece is checked. Before any content, the recipient receives a SHA-256 hash tree over every encrypted piece. Missing, reordered, swapped or altered pieces stop the transfer, and so does a file that changed on the sender's side partway through.
  • You see the offer first. Names and sizes are shown before anything downloads, and nothing downloads until you accept.
  • Previews run in a sandbox. Previews render in a frame with no access to this site's storage or links, and only for formats recognised from a file's own bytes. HTML and SVG are never rendered as pages.
  • A strict page. A content security policy blocks code from anywhere but this site. There are no third-party scripts, no analytics and no cookies.

What it does not protect against

  • Anyone with the link can receive the files. Share it only with your recipient. A room admits one recipient at a time, and a newer connection holding the link replaces an older one.
  • The code your browser runs comes from the server. A malicious or compromised server could serve code that leaks keys. That is true of every encrypted web app. What limits it: the code is open, you can run your own instance, and reproducible builds and browser-verified code are planned.
  • Metadata. The server sees sizes, timing and network addresses (see how it works).
  • Your own devices. Malware on the sender's or the recipient's device defeats any encryption. Received files are decrypted in your browser's storage until you leave the page.
  • No human cryptographer has audited it yet. The parcel format was reviewed in two passes by an AI reviewer and is checked against an independent implementation in every build. A human review is planned before a 1.0 release; a flaw found then is fixed in a new format version.

Find problems, and help fix them

  • Everything is public: the code, the format specification, its test vectors and the design decisions.
  • Point any tool at it, including AI agents. Fuzz the format, review the code, or attack an instance you run yourself. Please do not test instances that other people run, this one included, beyond normal use.
  • Report vulnerabilities privately through the repository's security page (Report a vulnerability). The policy is in SECURITY.md.
  • Fixes are welcome as pull requests. Changes to the parcel format need test vectors and new version numbers, never edits to a frozen version.
